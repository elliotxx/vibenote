# Data Safety

## 背景与目标

Vibenote 是一个极简纯文本笔记应用，核心体验是用户可以一直输入，不需要主动管理文件、格式或保存动作。因此“数据不丢失”不能只依赖用户手动备份，而要由应用在保存、恢复、误操作和图片资源四个层面提供保护。

相关实施计划见 [Data Safety Implementation Plan](../plans/2026-07-08-data-safety-implementation-plan.md)。

目标：

- 正常编辑时，保存过程不能产生半写入文件。
- 覆盖保存前保留可回滚版本，避免误删、格式化、AI 操作或应用 bug 直接覆盖唯一副本。
- 异常退出或启动时，能发现未完成写入和最近草稿，并给出恢复路径。
- 任意位置打开的 `.vibenote` 文件和粘贴图片都有清晰隔离，避免跨文件污染。
- 所有保护策略都能通过本地脚本或 e2e 验证，不依赖口头确认。

## 现状与问题

当前已经具备的数据保护能力：

- 主进程 `writeAtomic` / `writeAtomicSync` 使用临时文件加 `rename` 完成原子替换。
- 编辑器 350ms 自动保存，退出前走同步保存。
- `npm run verify:stability` 已验证长文本粘贴、快速退出和重新打开后的保存结果。
- 应用数据目录和外部文件已区分；应用数据目录图片会按文档派生 key 存放。

这些能力可以避免一部分“写一半”的问题，但还不够：

- 原子写入只能保证新旧文件二选一，不保证用户误删或 bug 覆盖后还能回滚。
- 当前没有版本化备份，也没有恢复入口。
- 当前没有启动时的异常恢复扫描，例如残留临时文件、更新的草稿恢复文件。
- 图片文件没有和文本快照形成可审计关系，恢复文本时可能只恢复了 Markdown 引用，无法判断图片是否还存在。
- 外部文件保存在任意目录，应用不能假设用户启用了 Time Machine 或 iCloud。

## 方案设计

### 分层防线

数据安全采用四层保护，而不是依赖单个保存动作：

| 层级 | 保护对象 | 设计 |
| --- | --- | --- |
| L1 原子保存 | 当前文件 | 继续使用临时文件写入后 `rename`，并在写入前创建目录。 |
| L2 覆盖前备份 | 上一个稳定版本 | 每次内容发生实质变化并将覆盖磁盘文件前，先保存旧内容快照。 |
| L3 草稿恢复 | 最新编辑内容 | 主保存前先写入恢复草稿；如果主保存失败或应用崩溃，启动时可以找回最新编辑内容。 |
| L4 资源隔离 | 图片和外部文件 | 图片按文档隔离；备份 manifest 记录图片引用和存在性。 |

### 文档身份

每个可保存对象都需要一个稳定 `documentId`：

- 默认 stream：使用固定 id `internal:stream`。
- 应用数据目录中的普通内部文件：使用 `internal:<relative-path-hash>`。
- 外部文件：使用规范化绝对路径的 SHA-256 摘要，形如 `external:<hash>`。

`documentId` 只用于内部备份目录和恢复索引，不写入用户正文。

### 备份目录

备份统一放在应用数据目录，避免污染用户任意位置文件夹：

```text
~/Library/Application Support/Vibenote/
  backups/
    <documentId>/
      manifest.json
      20260708-152233-120.vibenote
      20260708-153011-044.vibenote
  recovery/
    <documentId>.vibenote
```

`manifest.json` 记录：

- `documentId`
- 原始文件路径或内部相对路径
- 显示名
- 创建时间
- 文件大小
- 内容 hash
- 应用版本
- 图片引用列表和当时是否存在

manifest 也必须原子写入。

### 覆盖前备份

保存流程改为：

1. 解析 `identifier` 到真实文件路径。
2. 将当前编辑器内容写入 `recovery/<documentId>.vibenote`。
3. 读取磁盘上已有文件。
4. 如果已有内容和新内容不同，先写入备份快照。
5. 原子写入目标文件。
6. 成功后更新 manifest，并保留 recovery 文件作为最近草稿，或标记为已同步。

备份失败时不能静默吞掉。建议策略：

- recovery 写入失败：阻止保存并在状态栏提示，因为最新编辑内容没有安全落点。
- backup 写入失败：阻止覆盖目标文件，并提示“备份失败，已保留恢复草稿”。这样不会丢旧版本，也不会丢最新草稿。
- 主保存失败：保留旧文件和 recovery，状态栏提示保存失败。

### 保留策略

默认策略要足够安全，又不能无限占用磁盘：

- 同一文档最多保留 100 个快照。
- 自动保存只对相同内容去重；只要即将覆盖的旧内容没有快照，就创建覆盖前快照。
- 手动高风险操作始终创建快照，包括删除 block、格式化、AI 替换、清空 stream。
- 保留最近 24 小时内的所有高风险快照。
- 超限时删除最旧快照，并原子更新 manifest。

### 启动恢复

应用启动时扫描：

- `*.tmp` 残留文件。
- `recovery/<documentId>.vibenote` 比目标文件更新的草稿。
- manifest 中存在但目标文件缺失的外部文档。

首版使用非破坏性恢复：

- 默认不自动覆盖原文件。
- 在状态栏提示“发现可恢复草稿”。
- 用户可将恢复内容插入为新 block。
- 外部文件缺失时，只提示路径不可用，不自动创建同名文件。

### 图片安全

图片继续支持两种存储模式：

| 模式 | 目录 | 目标 |
| --- | --- | --- |
| 当前文件旁边 | `<document-name>.assets/` | 文件夹可随文档一起移动和分享。 |
| 应用数据目录 | `images/<documentAssetKey>/` | 不污染用户文件夹，且不同文档隔离。 |

备份文本时不默认复制图片二进制，避免每次快照复制大文件。manifest 记录图片绝对路径、文件大小和 hash。恢复时如果图片缺失，明确显示缺失状态，避免用户误以为图片已恢复。

后续如果需要强一致图片恢复，可增加“重要快照复制图片”选项，但不进入第一阶段。

## 自闭环验证范围

第一阶段可以完全本地验证：

- 覆盖保存前生成备份快照。
- 备份失败时不覆盖原文件，并保留 recovery。
- 主保存失败时保留旧文件和 recovery。
- 删除 block 或 AI 替换前强制生成高风险快照。
- 启动时发现比目标文件更新的 recovery。
- 外部 `.vibenote` 文件使用独立 documentId，备份不写到用户原目录。
- 应用数据目录图片按文档隔离。

## 验收标准

- 修改一个已有文件后，`backups/<documentId>/` 下出现可读取的旧内容快照。
- 保存过程中的临时文件残留不会被当成主文件加载。
- 人为模拟备份写入失败时，目标文件内容不变，recovery 中保留最新编辑内容。
- 人为模拟主保存失败时，目标文件内容不变，recovery 中保留最新编辑内容。
- 删除 block、格式化、AI 替换前都会创建高风险快照。
- 重新启动时，如果 recovery 比目标文件新，UI 能提示并允许插入为新 block。
- 外部文件备份目录位于应用数据目录，不在用户原文件旁边创建隐藏备份。
- 图片使用应用数据目录时，不同文档图片目录不同。
- `npm run verify:stability` 继续通过。

## 风险与边界

- 应用内备份不能替代磁盘级备份。磁盘损坏、用户删除整个 `~/Library/Application Support/Vibenote`、恶意软件或系统级清理仍需要 Time Machine、iCloud Drive 或其他外部备份。
- 备份会增加磁盘占用，需要保留策略和后续清理入口。
- 外部文件路径 hash 在文件移动后会变化，移动前后的备份需要通过 manifest 的原始路径和文件 hash 辅助识别。
- 文本快照和图片二进制不是强事务，第一阶段只保证文本可恢复和图片引用可审计。

## 非自闭环 Blocker

- 是否启用 iCloud Drive、Time Machine 或第三方同步无法由应用强制验证，只能在文档中建议。
- 恢复 UI 的最终交互文案可以继续微调，但不阻塞数据安全第一阶段。
- 图片是否需要随每个快照复制二进制属于存储成本和安全性的产品取舍，第一阶段先不做。

## 待确认点

- 备份保留上限是否接受默认 100 个快照。
- 是否后续增加“另存为恢复副本”和完整历史浏览器。
