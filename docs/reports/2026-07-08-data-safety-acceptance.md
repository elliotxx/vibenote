# Data Safety Acceptance

## 结论

数据安全第一阶段可以作为高 ROI 的首发保护方案：已覆盖正常保存、覆盖前备份、保存失败保护、恢复草稿、高风险操作快照和打包应用运行时验证。

本阶段不承诺云同步、完整历史浏览器、图片二进制随快照复制，也不承诺系统磁盘损坏时恢复。恢复入口当前采用状态栏按钮，点击后将 recovery 插入为新 block，不覆盖原文件。

## 已实现能力

- 保存链路先写 recovery，再写覆盖前备份，最后原子写入目标文件。
- 备份失败时阻止覆盖目标文件，保留旧文件和最新 recovery。
- 删除 block、删除空 block、删除图片、格式化、AI 写入前创建高风险快照。
- 启动后扫描 recovery，发现比目标文件更新的草稿时在状态栏提示，并支持插入为新 block。
- 备份 manifest 记录文件来源、内容 hash、应用版本和图片引用。
- 测试运行支持隔离数据目录，不触碰用户真实 Vibenote 数据。

## 关键验收点

- 覆盖前备份：运行时脚本读取 manifest 和快照文件，确认快照中保留了被覆盖前的稳定内容。
- 保存失败保护：运行时脚本将 backups 路径伪造成普通文件，确认保存失败时目标文件没有被覆盖，recovery 保存了最新尝试内容。
- 高风险快照：e2e 用例拦截 `snapshotSync`，确认删除 block 前先创建快照；快照失败时删除动作停止。
- 非破坏性恢复：e2e 用例模拟 recovery，点击“恢复草稿”后确认当前内容保留，恢复内容作为新 block 插入。
- 回归修复：新增 e2e 暴露了删除第一个 block 后 selection 越界的问题，已修复并由全量 e2e 覆盖。

## 副作用与边界

- 每次实质覆盖前都会保留旧内容快照，磁盘占用会增加；当前每个文档最多保留 100 个快照。
- 保存路径变严格：如果 recovery 或 backup 写入失败，应用会拒绝覆盖目标文件。这会让用户看到保存失败，但避免旧版本被破坏。
- 高风险操作前同步创建快照，极端情况下会带来轻微交互延迟；当前只在删除、格式化、AI 写入等破坏性动作前触发。
- recovery 现在支持插入为新 block；尚未提供历史浏览器或另存为恢复副本。
- 应用内备份不能防止用户删除整个应用数据目录、磁盘损坏、恶意软件或系统级清理；这些仍需要 Time Machine、iCloud Drive 或外部备份。

## 后续建议

下一阶段可补备份管理入口：查看快照、恢复历史版本、清理旧备份，并增加“另存为恢复副本”。这些能力价值明确，但比当前首发数据保护主干更重。
